# 프로젝트 검토와 고도화 순서 — 2026-11-17

현재 프로젝트의 강점은 서로 다른 LoL 경기 자료를 SQL·Python으로 분석하고 개인 복기 서비스까지 구현한 점이다. 우선 보완할 부분은 분석에 들어가는 데이터의 재현성과 품질 통제다. 이번에는 독립 실행 가능한 배치 파이프라인을 추가했다. [실행·구조·장애 대응](25_data_pipeline.md)

## 검토 범위

`src/`, `sql/`, `api/`, `scripts/`, `service/`, 테스트, Docker·CI 설정, 기존 분석 문서와 로컬 원본·저장된 집계의 건수를 대조했다. 작업 시작 시 서비스·프런트엔드·문서에 미커밋 변경이 있었으므로, 아래의 서비스 현황에는 로컬 작업본에서 확인한 내용도 포함한다. 이번 커밋은 새 파이프라인과 직접 관련된 변경으로 한정한다.

실제 계정 조회·Riot 추가 수집·모델 추론·외부 배포는 실행하지 않았다. 키·개인 식별자·개인 전적·원본 데이터는 새 공개 파일에 포함하지 않는다.

클러스터링 결과를 예측 모델의 성능으로 설명하지 않는다. 현재 LLM 기능은 제공된 지표에서 확인할 초점과 근거를 고르는 제한된 기능이다. 관측 사실·지표 계산은 Python이 담당하며, 장면 이해·승패 원인 판단·실력 향상 효과를 검증한 상태가 아니다.

## 발견한 문제와 이번 대응

1. **기존 적재기는 전체 DB를 삭제한 뒤 다시 생성한다.** `src/load.py`의 기존 실행 방식은 연구 재현용으로 유지하고 새 배치는 `.local/pipeline/`에서 실행한다. 검증이 실패하면 게시 레지스트리는 이전 성공본을 유지한다.
2. **기존 검증기는 조회 결과를 출력한다.** 새 배치에서는 중복 키·필수 값·수치 범위·승패 형식·참여자 완전성·마트 분모가 통과해야 게시할 수 있다. 소수 형태의 승패가 정수 변환으로 숨겨지지 않도록 기존 로더에 선택적 `strict=True` 검사를 추가했다.
3. **경기 단위 불완전성이 팀 지표에 영향을 준다.** 역할 필터 후 일부 참여자가 빠지거나 같은 팀 역할이 중복될 수 있다. 새 마트에서는 해당 경기 전체를 격리하고, 완전한 경기에서 팀 킬·KP를 다시 계산한다. 격리 사유와 건수를 남긴다.
4. **입력·분석 버전과 게시 이력이 분리되어 있지 않다.** 원본 바이트와 변환 코드·SQL의 SHA-256을 기록한다. 같은 날짜의 재시도는 최초 입력을 재사용하고, 정정은 명시적으로 새 스냅샷을 만든다. 과거 배치를 재처리해도 최신 날짜의 게시본은 유지한다.
5. **서로 다른 자료의 시점이 혼재한다.** 로컬 도감은 16.19.1, KR 메타 파일은 2026-10-04 수집한 16.19·282경기·2,820참여 행이다. 현재 수집 코드는 티어 층화를 지원하지만, 저장된 파일의 출발 표본은 SILVER II다. 코드의 새 기능을 기존 표본의 수집 방식으로 소급하지 않는다.
6. **현재 도감과 과거 챔피언 문자열의 대소문자가 다르다.** 실제 정규화 자료에 `FiddleSticks` 표기가 있었다. 도감 ID와 대소문자를 무시하고 연결한 후 공식 ID로 통일한다. 새 도감은 한국어 이름 연결에만 사용하며 과거 능력치 자료로 사용하지 않는다.

완전한 경기만 남기는 정책은 기존 집계와 다른 분석 모집단을 만든다. 따라서 기존 `outputs/`의 수치를 새 마트 결과로 덮어쓰지 않으며, 두 결과를 비교할 때 필터와 분모를 함께 제시한다.

## 실제 배치 검증

로컬의 기존 원본을 사용한 2026-11-17 입력 배치에서, 기존 패치·큐·역할 필터 후 **83,566행**을 확인했다. 새 완전성·시간 범위 조건에 따라 **158경기·1,566행**을 격리하고 **8,200경기·82,000행**으로 새 마트를 만들었다. 원본 DB와 기존 분석 CSV는 변경하지 않았다. 상세 검사 결과와 실행 범위는 [파이프라인 문서](25_data_pipeline.md)에 기록한다.

이는 데이터 품질 정책을 적용한 처리 건수이며 서비스 이용·매출·유지율 개선 성과가 아니다. 원본 두 파일의 전체 행은 각각 40,410행과 68,300행이며, 83,566행은 기존 필터를 통과한 참여 행 기준이다.

[Linux CI 실행](https://github.com/jinwon25/lol-live-ops-analytics/actions/runs/44107889851)에서 Airflow 3.4.0 이미지 빌드·의존성 검사·DAG 파싱과 실제 Task SDK 실행을 확인했다. 합성 입력 64경기·640행으로 네 작업이 성공하고 검증본이 게시되었다. 실제 원본의 전체 처리는 로컬 CLI에서 검증했으며, Airflow에서의 장기 스케줄 운영은 후속 범위다.

## 다음 고도화 순서

1. **Airflow 운영·복구 확인.** Linux CI에서 합성 정상 배치는 실행했다. 로컬 UI에서 품질 실패 → 정정 → 성공본 게시 과정을 재현하고, 스케줄·재시도·감사 이력을 함께 확인한다. 이번 저장소에 별도 Compose와 CI 실행 경로를 추가했다.
2. **새 마트와 BI 연결.** 표본 수·격리 수·수집 시점·패치·코호트·역할 분모를 화면에 함께 표시한다. 현재 서비스의 과거 근거 화면과 최신 메타 화면은 출처를 구분해서 유지한다.
3. **Riot 증분 수집.** 기존 `RiotGateway`의 공유 예산을 재사용하고, 고정한 시작·종료 시각과 Match ID 중복 제거·지연 도착 재조회 범위를 정의한다. PUUID·키·원본 응답은 비공개로 두고 집계만 소비한다. 기존 rolling-window 수집 스크립트를 그대로 DAG로 감싸면 재실행 때 입력 기간이 움직이므로 먼저 계약을 바꿔야 한다.
4. **근거 조회 도우미.** 패치·코호트·최소 표본을 검증하는 제한된 조회 도구로 마트를 읽고, 응답마다 데이터셋·분모·출처를 남긴다. 사실 불일치·부적절한 비교·표본 부족·도구 실패를 포함한 평가 사례를 먼저 만든다.
5. **작은 예측 기준선.** 경기 시작 전 또는 특정 시점의 예측 질문을 먼저 고정한다. 최종 골드·최종 KDA·승패를 드러내는 값을 특징으로 사용하지 않고, 시간 순 학습/검증·동일 경기 분리·단순 기준선·확률 보정을 비교한다. 현재 데이터로 검은사막의 이탈·매출을 검증했다고 설명하지 않는다.
