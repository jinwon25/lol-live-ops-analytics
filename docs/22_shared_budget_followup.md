# 프로젝트 현황과 공유 요청 예산 보강 — 2026-11-15

현재 프로젝트는 과거 LoL 경기 분석 자료와 개인 전적 복기용 FastAPI 서비스를 함께 제공한다. 개인용 MVP의 조회·보관·복구 기능은 구현되어 있으며, 이번 작업은 여러 작업자가 Riot API 요청 한도를 공유하는 경로의 결함을 보완했다. 기존 미커밋 변경과 개인 자료는 보존했다.

## 현재 기능과 남은 범위

| 영역 | 구현 상태 | 남은 검증·제한 |
| --- | --- | --- |
| 전적 복기 | 최근 경기 조회, 6개 지표, 팀 비교·타임라인, 자동 리포트 | 이번 작업에서 실제 계정 요청은 실행하지 않음 |
| 개인 기록 | 리포트 50개·행동 노트 10개, 백업·복원·삭제 취소 | 전체 브라우저 회귀·모바일 확인이 남음 |
| AI | 로컬 서버 준비 상태 확인·재확인, 기존 코칭 실험 | 연결 성공과 실제 추론·코칭 유용성은 별도 |
| 분석 자료 | 과거 EUN 15.1·15.3 분석과 KR 16.19 제한 표본 | 현재 패치 자료로 간주하지 않으며 자동 갱신은 미구현 |
| 실행 기반 | 공유 요청 예산, Redis 캐시, SQLite 동기화 API, DB 볼륨 | 브라우저와 서버 기록의 자동 동기화·공개 사용자 인증은 미구현 |

기존 개선은 [보관·복구](19_storage_and_local_service_hardening.md), [AI 상태·행동 노트](20_runtime_and_notes_followup.md)에 정리했다. Ponytail의 최소 변경 원칙에 따라 기존 요청 예산 계층을 수정하고 런타임 의존성은 추가하지 않았다. 완료 전 검증 스킬에 따라 실제 실행 결과와 준비만 한 검사를 분리했다.

## 이번에 수정한 문제

1. **긴 대기 시간을 짧은 대기 시간이 덮어쓰는 문제:** 기존 Redis `SET`은 다른 작업자의 더 긴 `Retry-After`를 지웠다. Lua 안에서 현재 만료 시각과 새 만료 시각 중 큰 값을 선택하고 TTL도 함께 갱신한다.
2. **작업자 간 시계 차이:** 예약·응답 헤더 반영·대기 시간 갱신이 Redis `TIME`을 사용한다. 단일 프로세스 경과 시간 측정은 기존 `time.monotonic()`을 유지한다.
3. **호출 한도 0의 첫 요청 허용:** 메모리·Redis 경로 모두 0 한도에서는 예약을 거부한다. 새 한도가 관측될 때까지 해당 범위를 차단하며, 다른 메서드의 독립 예산은 유지한다.
4. **메모리 정리가 요청 한도 기록도 삭제하는 문제:** Compose의 `allkeys-lru`를 `noeviction`으로 변경했다. 메모리가 부족하면 쓰기 오류를 통해 새 예약을 중단하는 편을 선택했다. 캐시와 예산을 함께 보관하므로 가용성이 낮아질 수 있으며, 장기 운영에는 저장소 분리를 검토해야 한다.
5. **검사 범위 보완:** 실제 Redis에서 동시 예약·메서드별 한도·대기 연장과 만료·작업자 시계 차이·Lua 오류 뒤 복구를 검사하는 5개 통합 검사를 추가했다. CI의 Redis 7 서비스 컨테이너에서 별도 실행한다.

## 참고한 공식 근거

- [Riot 요청 제한 안내](https://developer.riotgames.com/docs/portal/): 429 응답의 `Retry-After` 기간 동안 후속 요청을 중단한다. 여러 대기 시간 중 긴 것을 보존하는 것은 이 요구를 적용하기 위한 프로젝트 구현이다.
- [Redis Lua 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/): 조건 확인과 변경을 하나의 원자적 스크립트로 처리한다. 원자성은 오류 시 전체 롤백이나 Redis 재시작 후 복원을 의미하지 않는다.
- [Redis TIME](https://redis.io/docs/latest/commands/time/): 공유 기록은 Redis 서버의 시각을 사용한다.
- [Redis 메모리 정리 정책](https://redis.io/docs/latest/develop/reference/eviction/): `noeviction`은 키를 자동 축출하지 않고 메모리 추가가 필요한 쓰기에 오류를 반환한다. 해당 정책 선택은 요청 한도 기록을 보존하려는 프로젝트 판단이다.
- [GitHub Actions Redis 컨테이너](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-redis-service-containers): Ubuntu 작업의 서비스 컨테이너와 상태 확인을 사용한다.

## 실행한 검증

- Python 전체: **73개 통과, Redis 통합 5개 건너뜀**. 물리 CPU 수 조회 실패로 논리 코어를 사용한다는 기존 joblib 경고 1개가 있었다.
- JavaScript: **30개 통과**. 기존 리포트·수동 복기·분석·행동 노트 검사를 함께 실행했다.
- 회귀 재현: 새 0 한도 검사를 이전 HEAD의 메서드에 메모리에서만 적용하면 실패하고 현재 메서드에서는 통과한다. 원본 파일이나 미커밋 코드를 되돌리지 않았다.
- 변경 Python 구문과 CI·Compose YAML 구조를 확인했다.

현재 환경에는 Redis 실행 파일·Python Redis 패키지·Docker가 없어 실제 Lua 실행은 확인하지 못했다. 통합 검사는 별도 Redis 클라이언트와 예산 객체 두 개를 같은 테스트 프로세스에서 실행한다. 서로 다른 OS 프로세스 부하 시험과는 구분한다. Lua 오류 복구 검사는 합성 잘못된 자료형을 사용하며 실제 네트워크 단절·서버 재시작 시험을 대신하지 않는다. CI 설정은 추가했지만 원격 실행 결과는 없다. Ruff·Mypy·커버리지·Docker·전체 브라우저 검증도 이번에 완료하지 않았다.

실제 Redis 검사에는 프로젝트 의존성을 설치한 환경과 테스트용 Redis가 필요하다. 프로젝트 루트에서 다음과 같이 실행한다.

```powershell
$env:TEST_REDIS_URL = 'redis://127.0.0.1:6379/15'
python -m pytest tests/test_redis_integration.py -q
Remove-Item Env:TEST_REDIS_URL
```

환경 변수가 없으면 명시적으로 건너뛰며, 지정했는데 연결하지 못하면 실패한다. 검사마다 UUID로 격리된 합성 키를 쓰고 그 키만 삭제한다. `FLUSHDB`나 서버 설정 변경은 수행하지 않는다. 실제 Riot 호출도 없다.

## 다음 우선순위

1. 실행 가능한 환경에서 새 Redis 통합 검사와 기존 브라우저·Docker·정적 검사·커버리지를 완료한다.
2. 장기 운영이 필요하면 캐시와 예산 저장소 분리, Redis 재시작 시 예산 복구, 응답 헤더 순서 역전·실제 다중 프로세스 부하를 검증한다. 현재 Compose Redis는 영속화를 끈 상태이며, 이번 수정으로 재시작 시 한도 기록 보존을 보장하지 않는다. Redis Cluster도 별도 키 배치 설계가 필요하다.
3. 현재 패치 자료 갱신은 공식 자료 버전·표본 출처·API 예산을 명시한 수집 절차로 진행한다. 오래된 표본의 수치를 최신 통계처럼 표시하지 않는다.
4. 실제 코칭 품질은 서버 상태 확인과 분리해, 비식별 평가 사례와 사실 보존·유용성 기준으로 평가한다.
